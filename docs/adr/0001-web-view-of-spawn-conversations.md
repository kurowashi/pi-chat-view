# ADR 0001: 子エージェント同士の会話をローカル Web ページで見る

- 状態: 採用
- 日付: 2026-09-28
- 対象: 拡張の入口、待ち受け、スレッド同定、表示項目

## 背景

- pi-spawn の子は `message_agent` で兄弟へ話しかけ、返信は次のターンとして届く。会話は子セッションの JSONL に残るが、
  1ファイルは1人の視点なので、会話として読むにはファイルを突き合わせる必要がある。
- pi-spawn 自身はこの用途を対象外にした。完了後の run を開く手段は `pi --session <path>` だけで、
  TUI の `/spawn logs` は実行中のみを対象にする（[pi-spawn ADR 0005](https://github.com/kurowashi/pi-spawn/blob/main/docs/adr/0005-child-observability.md)）。
- 既存の第三者の Pi 用 Web ビューアはセッション1本を1ビューとして表示する（例: pi-web、pi-sessions-viewer）。
  複数セッションを1本の時系列へマージするものは無い。
- 実データでは、1回の会話が 2ファイルに分かれ、`resume_run_id` のラウンドは同じ2ファイルへ追記されていた。
  さらに、resume 後の run id はファイル名のセッション id と一致しない（実測: `SessionManager.findById(cwd, "98e5d8af", spawnSessions)`
  は NOT FOUND。ファイルの header id は `f83c6332` のまま）。

## 決定

1. pi-spawn 本体ではなく、独立したプラグイン（`pi-chat-view`）にする。結合はファイル形式だけとする。
2. 既存の `<agentDir>/spawn-sessions/*.jsonl` を読み取り専用で読む。新しい記録・状態・書き込みを持たない。
3. スレッドは、子のタスク先頭にある兄弟一覧（sibling ブリーフィング）の参照による連結成分とする。
   同じ spawn 呼び出しの子が1スレッドになり、resume は同じファイルへの追記なので同じスレッドの続きになる。
4. スレッドの同定と表示名の復元に run id を使わない。存在するファイルの id を辺にした参照だけを使う。
5. 発言の正は送信側の `message_agent` 呼び出しとする。受け手に残る複製は、本文の一致で落とす
   （ヘッダー `message_agent from_run_id=…` 付きと、ヘッダーなしの両形式に対応する）。
6. 表示は4種（発言・描写・指示・ツール呼び出し）に加え、reasoning を独立したトグルにする。
   reasoning とツール呼び出しは既定で非表示。トグル状態は URL に残す。
7. サーバーは `node:http` の素の実装とし、依存ゼロ・ビルド工程なし・1枚の HTML で完結させる。
   待ち受けは `127.0.0.1` のみ、GET 以外は 405。
8. 起動はユーザーのコマンド `/chat-view` のみで行う。読み込み時には何もしない。
   停止は `/chat-view stop` と `session_shutdown` の両方から同じ冪等な経路に収束させる。
9. 追記の反映はページからのポーリング（1.5秒、タブ非表示中は停止）とし、サーバー側にタイマーを持たない。
10. 一覧は最終更新の新しい順に100件。`?limit=` で最大1000件。

## 理由

- 別プラグインにすると、pi-spawn のツール予算・待機モデル・resume 規則を変えずに済み、片方の失敗が他方へ波及しない。
- ファイル形式だけに依存すれば、pi-spawn 側の改修（run id 規則の変更など）が視聴側を壊しにくい。
- 読み取り専用とループバック限定を組にすると、認証を持たなくても妥当な脅威モデルになる。
- 兄弟一覧は子自身が持つ唯一の「誰と話せるか」の記録で、親セッションの走査（数百MB）を避けられる。
- run id を使わないことで、resume のたびに変わる id とファイル名の不一致を回避できる。
- 送信側を正にすると、話者と宛先が確実に分かる。受信側の複製は話者が文脈からしか分からない。
- SSE や WebSocket は接続管理と再接続の実装を増やす。会話の更新頻度ではポーリングで十分で、
  ページを閉じればサーバー側の仕事も止まる。
- `pi --export` の HTML は単一セッションの静的出力で、複数セッションの時系列マージも逐次更新もできない。

## 帰結

- 拡張の恒久コストは、コマンド1つの表示文字列だけ。ツール定義は 0 トークンで、会話内容もシステムプロンプトも変えない。
- Pi のプロセスに読み取り専用のソケットが1つ増える（`/chat-view` を実行したときだけ。終了時に閉じる）。
- 表示は最大1.5秒遅れる。実行中の子を完全なリアルタイムで見る用途には向かない。
- 兄弟一覧を持たない子（兄弟なし、`inheritConversation` で親の会話を継承した子など）は単独スレッドになる。
- run id からスレッドを引けない。ユーザーは一覧から選ぶ。
- 一覧は100件で打ち切るため、古いスレッドは `?limit=` を明示しないと出ない。
- 会話の意味づけ（誰が話者か、どの発言が誰宛か）は文字列に依存する。pi-spawn のブリーフィング形式が変わったら追随が要る。

## 代替案

| 代替 | 却下理由 |
|---|---|
| pi-spawn に Web ビューを内蔵する | 一覧・探索規則が spawn のコアへ入り込む。ADR 0005 が避けた結合を作り直すことになる |
| TUI のビューを拡張する | 画面が1つのため複数列の比較ができない。そもそも端末外から見られない |
| 親セッションも同じ時間軸に混ぜる | 親は `sessions/` にあり走査が重く、子の結果・usage・内部ターンがノイズになる |
| run id を親セッションの走査で解決する | 初回スキャンが数百MB に達する。resume 後の run id は保存先と一致しない |
| 静的 HTML を `pi --export` 相当で書き出す | 実行中の追記が見えず、複数セッションのマージもできない |
| SSE / WebSocket で逐次更新する | 接続管理・再接続・ハートビートの実装が増える。1.5秒の遅延は会話の読解では問題にならない |
| 既存の第三者ビューア（pi-web 等）を併用する | 単一セッション表示であり、兄弟の会話は1本にならない |
| ブラウザを自動で開く | 副作用を増やさない。URL の通知で足りる |
| 表示側で reasoning を要約・省略する | 表示は記録に忠実であるべきで、要約はモデル呼び出し（コスト）を持ち込む |
