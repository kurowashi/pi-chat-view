# ADR 0001: 子エージェント同士の会話をローカル Web ページで見る

- 状態: 採用
- 日付: 2026-09-28
- 対象: 拡張の入口、待ち受け、スレッド同定、表示項目

## 結論

- pi-spawn 本体ではなく、独立したプラグイン（`pi-chat-view`）として実装します。結合は子セッション JSONL の形式だけです。
- 既存の `<agentDir>/spawn-sessions/*.jsonl` を読み取り専用で読み、兄弟の会話を1本の時系列に並べます。
- スレッドは、子のタスク先頭にある兄弟一覧（sibling ブリーフィング）の参照による連結成分とします。
- 発言の正は送信側の `message_agent` 呼び出しとし、受け手に残る複製は本文の一致で落とします。
- `/chat-view` で `node:http` のサーバーを起動し、`127.0.0.1` のみで待ち受けます。Pi の終了時に閉じます。
- 追記の反映はブラウザからのポーリングで行い、サーバー側にタイマーも状態も持ちません。

## 背景

pi-spawn の子は `message_agent` で兄弟へ話しかけ、返信は次のターンとして届きます。
会話は子セッションの JSONL に残りますが、1ファイルは1人の視点なので、会話として読むには複数のファイルを突き合わせる必要があります。

pi-spawn 自身はこの用途を対象外にしました（[pi-spawn ADR 0005](https://github.com/kurowashi/pi-spawn/blob/main/docs/adr/0005-child-observability.md)）。
完了後の子を開く手段は `pi --session <path>` だけで、TUI の `/spawn logs` は実行中のみを対象にします。

2026-09-28 に確認した次の3例では、いずれもセッション1本を1ビューとして表示するもので、複数セッションを1本の時系列へマージする機能は確認できませんでした。
確認した例: [pi-web](https://github.com/agegr/pi-web/)、[pi-sessions-viewer](https://github.com/ygncode/pi-sessions-viewer)、[sessions-viewer](https://github.com/skorotkiewicz/sessions-viewer)。

2026-09-28 に実データを確認したところ、1回の会話は2ファイルに分かれ、`resume_run_id` のラウンドは同じ2ファイルへ追記されていました。
当時、resume 後の run id はファイル名のセッション id と一致しませんでした（[実測メモ](#実測メモ)）。
同日の pi-spawn `a640928` で子の宛先は run id から session id + entry id へ変わり、この不一致は解消されています。

## 決定

1. pi-spawn 本体ではなく、独立したプラグイン（`pi-chat-view`）にします。
2. 既存の `<agentDir>/spawn-sessions/*.jsonl` を読み取り専用で読みます。新しい記録・状態・書き込みを持ちません。
3. スレッドは、子のタスク先頭にある兄弟一覧の参照による連結成分とします。
4. 子の識別子（run id / session id / entry id）を使いません。存在するファイルの id を辺にした参照だけを使います。
5. 子が継承した親の履歴は、親セッションのファイルにある entry id との照合で切り分け、子の会話として表示しません。
6. 過去の位置から再開して分岐した子は、最後の entry から `parentId` をたどった分岐だけを表示します。分岐を読み取れないファイルは書かれた順にすべて表示します。
7. 発言の正は送信側の `message_agent` 呼び出しとします。受け手の複製は、本文が一致する場合だけ除外します。
8. 表示は5種（発言・描写・指示・reasoning・ツール呼び出し）とします。reasoning とツール呼び出しは既定で非表示にします。
9. サーバーは `node:http` の素の実装とし、ページは1枚の HTML で完結させます。待ち受けは `127.0.0.1` のみ、GET 以外は 405 とします。
10. 起動はユーザーのコマンド `/chat-view` のみで行います。読み込み時には何もしません。
11. 停止は `/chat-view stop` と `session_shutdown` の両方から同じ冪等な経路に収束させ、起動処理が進行中でも起動したサーバーを閉じます。
12. 追記の反映はページからのポーリング（1.5秒、タブ非表示中は停止、一覧は7.5秒）とし、サーバー側にタイマーを持ちません。
13. 一覧は最終更新の新しい順に100件とし、`?limit=` で最大1000件まで増やせます。

## 理由

- 別プラグインにすると、pi-spawn のツール予算・待機モデル・resume 規則を変えずに済みます。
- 結合をファイル形式だけにすれば、pi-spawn 側の改修が視聴側を壊しにくくなります。
- 読み取り専用とループバック限定を組にすると、認証を持たなくても妥当な脅威モデルになります。
- 兄弟一覧は子自身が持つ唯一の「誰と話せるか」の記録で、親セッションの走査を避けられます。
- run id を使わないことで、pi-spawn の宛先の変遷（`to` → `target_run_id` → `target_session_id`）に追随せずに済みます。
- 最後の entry からたどる分岐だけを読むことで、`resume_entry_id` で破棄した分岐を会話に混ぜずに済みます。
- 送信側を正にすると、話者と宛先が確実に分かります。受信側の複製は話者が文脈からしか分かりません。
- ポーリングは接続管理・再接続・ハートビートを持ち込みません。ページを閉じればサーバー側の仕事も止まります。
- `pi --export` の HTML は単一セッションの静的出力で、複数セッションの時系列マージも逐次更新もできません。

## 帰結

- 拡張の恒久コストは、コマンド1つの表示文字列だけです。ツール定義は 0 トークンで、会話内容もシステムプロンプトも変えません。
- Pi のプロセスに読み取り専用のソケットが1つ増えます。増えるのは `/chat-view` を実行したときだけで、終了時に閉じます。
- 表示は最大1.5秒遅れます。完全なリアルタイムが必要な場合は `pi --session <path>` を使います。
- リクエストごとにファイルを読み直すため、I/O は開いているタブ数と子セッション数に比例して増えます。
- 兄弟一覧を持たない子は単独スレッドになります。
- run id からスレッドを引けません。ユーザーは一覧から選びます。
- 一覧は100件で打ち切るため、古いスレッドは `?limit=` を明示しないと出ません。
- 話者と宛先の意味づけは文字列に依存します。pi-spawn のブリーフィング形式が変わったら追随が要ります。
- 親セッションのファイルが削除されている場合、継承した履歴を切り分けられず、子の会話に混ざります。

## 代替案

| 代替 | 却下理由 |
|---|---|
| pi-spawn に Web ビューを内蔵する | 一覧と探索規則が spawn のコアへ入り込む |
| TUI のビューを拡張する | 画面が1つで比較できず、端末外から見られない |
| 親セッションも同じ時間軸に混ぜる | 走査が重く、子の結果や usage がノイズになる |
| run id を親セッションの走査で解決する | 全走査が必要で、run id は保存先と一致しない |
| 静的 HTML を書き出す | 実行中の追記が見えず、マージもできない |
| transcript を書かれた順に全部読む | 分岐した子で、破棄した分岐が会話に混ざる |
| SSE / WebSocket で逐次更新する | 接続管理・再接続・ハートビートの実装が増える |
| 既存の第三者ビューアを併用する | 2026-09-28 に確認した3例では、兄弟会話の統合機能を確認できなかった |
| ブラウザを自動で開く | 副作用を増やさない。URL の通知で足りる |
| reasoning を要約・省略する | 表示は記録に忠実であるべきで、要約はモデル呼び出しを持ち込む |
| サーバー側にファイル内容のキャッシュを持つ | リクエスト間の状態が増える。必要な I/O はこの規模では問題にならない |
